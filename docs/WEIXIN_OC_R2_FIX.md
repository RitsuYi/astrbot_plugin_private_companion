# R2：首次微信绑定身份修复

版本：7.1.6+weixin.2。日期：2026-11-08。

## 实际根因

R1已经把微信纳入受支持平台，但首次绑定最终仍调用通用的 `derived_identity()`。
它的ASCII分支仅允许字母、数字、下划线和短横线，微信发送者形如 `opaque-peer@im.wechat`，
因此被拒绝并返回 `host_identity_invalid`。

测试中使用“爱弥斯”作为平台实例ID、微信原生发送者ID及旧通配模板，可以在R1准确复现这个错误。
平台实例中文名称本身通过原有校验。`account_id` 采用平台实例是本适配的内部路由约定，
并不等于微信登录账号，也不意味着它必须与 `weixin_oc_account_id` 相同。

## 修复

- `astrbot_host/identity_derivation.py`：允许有界的原生 `名称@域` ID；仍拒绝冒号、斜杠、空白、
  控制字符和通配符。新的带@账号派生为哈希存储键，既有有效账号的Bot及人格存储键不变。
- `astrbot_host/controller.py`、`astrbot_host/multi_controller.py`：先验证身份，再写待确认绑定；
  失败不会写出一个明知无效的新候选。多目标绑定错误也会报告具体校验字段。
- 版本标记升为R2，并增加首次绑定、管理员确认精确窗口、重载后回复与记忆写入的测试。

没有修改AstrBot文件、微信登录账号、长期记忆数据库结构或用户人格。
没有直接读取或复制真实微信凭证。没有自动授予新用户核心管理员权限。

## 为什么旧通配模板还会存在

首次绑定命令先保存待确认窗口；Dashboard管理员确认后，原有代码会新增精确目标，
并让它优先匹配该微信发送者。原通配模板可以保留作为其它会话的模板。
修复后的验收标准是实际窗口匹配精确发送者，而不是要求配置中彻底不存在 `*`。

## 已有R1候选

R1可能已保存了带@的合法微信候选，但后续校验失败。安装R2后它可重新被正常读取。
如果重新绑定提示已有另一候选，可先用 `companion_unbind` 清除未确认候选再绑定。
已确认管理员的更换仍走原来的管理页面流程，不能被任意一条新消息覆盖。

安装与用户侧验收见 `WEIXIN_OC_COMPAT.md`，测试结果见 `WEIXIN_OC_TEST_RESULTS.md`。
